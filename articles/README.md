## 首篇文章提纲

**拟定标题：《AI 友好的数据管理：宣言》**

**写作目标：** 解释为什么发起本书，给出工作定义和初版价值主张，展示全生命周期参考框架，并邀请读者参与后续修订。

**当前状态：** 详细提纲。以下价值主张为候选表述，尚未形成审定宣言。

### 第一部分：目的——为什么写这本书

需要说明：

- 在模型训练、知识问答、智能体执行和长期任务中，数据的组织、供给与维护会影响实际使用表现。
- 本书希望帮助从业者和使用者改善任务效果、效率和成本，并说明改进需要付出的管理与维护工作。
- 全书从具体问题出发，提供原则、结构、步骤、案例和验证方法，让不同背景的读者能够选择适用内容。

建议采用一个贯穿开篇的演示场景：同一项目存在旧需求、最新决定和历史讨论，AI 在执行任务时引用了已经失效的信息。展示原始材料的组织问题，但在没有实验之前，不给出准确率或成本提升数字。

本部分的预期产物是一段明确的写作目的，以及读者可以对照自身工作识别的典型问题清单。

### 第二部分：定义——什么是 AI 友好的数据管理

建议围绕以下工作定义展开，正式表述待审定：

> AI 友好的数据管理，是面向具体 AI 任务及其约束，对数据的获取、组织、供给、使用、更新与退出进行设计和维护，使数据能够被正确理解、适当使用和持续核验，并通过任务结果评价其效果、效率与成本。

需要进一步解释：

- “友好”具有任务和环境条件，不能仅根据文件格式或数据数量判断。
- 被管理的对象包含原始数据及其衍生物，例如训练样本、检索单元、上下文、工具观察、记忆和反馈记录。
- 数据管理既涉及内容与结构，也涉及来源、版本、权限、时间、质量和维护责任。
- Markdown 可以作为一种表达方式；具体采用何种格式、存储和查询机制，需要结合数据和任务判断。

建议提供一张小型对照表，解释“原始材料”“面向任务提供的数据”“需要持续维护的记录”之间的关系。对照使用同一个演示场景，避免引入过多新概念。

### 第三部分：价值主张——宣言的候选条目

借鉴敏捷宣言式的价值排序表达，先提出以下候选条目供讨论：

| 候选价值主张 | 需要在正文解释的含义 |
| --- | --- |
| 任务可用性，高于单纯扩大数据规模 | 数据是否有用，应结合目标任务和结果判断；规模仍可能是必要条件 |
| 语义清晰与证据可追溯，高于仅追求格式统一 | 统一格式需要服务于准确理解、来源核查和正确使用 |
| 按需供给与动态维护，高于一次性全量投入 | 选择、更新和撤回信息，应成为数据供给过程的一部分 |
| 真实任务验证与持续修正，高于未经验证的效果判断 | 用明确基线、结果和失败案例检查方法，保留修订空间 |
| 可控使用与责任明确，高于无条件扩大访问 | 说明数据可以用于什么、由谁维护、何时失效及如何追责 |
| 可复用的组织与协作，高于反复进行临时整理 | 沉淀来源、结构、模板和决策记录，同时控制维护成本 |

正文需要说明：价值排序不表示右侧事项没有价值，也不构成所有场景中的固定优先级。每条都应配一个具体含义、一个适用条件或反例，避免只发布口号。

本部分预期形成“宣言草案 v0.1”。是否保留六条、如何措辞及各条边界，均待主编审定和案例检验。

### 第四部分：全生命周期参考框架

建议用一张参考框架图配合下表说明主要环节。图应包含反馈与更新关系，并说明采用已有模型的应用可以跳过模型训练路径。

| 环节 | 主要数据对象 | 重点问题 |
| --- | --- | --- |
| 目标与任务定义 | 需求、约束、成功标准、任务样本 | 要改善什么，如何判断结果？ |
| 获取、组织与治理 | 来源数据、语义、标识、权限、版本 | 数据从哪里来，怎样理解和控制使用？ |
| 训练与适配 | 训练样本、标注、偏好、合成数据 | 数据如何形成可检查、可复现的训练输入？ |
| 检索、推理与上下文 | 知识单元、证据包、输入输出、上下文 | 当前任务应该获得什么信息，以何种方式获得？ |
| 智能体与记忆 | 任务状态、工具记录、事实、事件、经验 | 执行过程和长期信息怎样保持一致、可信和可维护？ |
| 评测、反馈与持续优化 | 评测集、失败记录、反馈、改进实验 | 如何定位问题、验证改变并处理退化？ |
| 更新、归档与退役 | 原件及索引、缓存、记忆等衍生物 | 数据何时失效，变化和退出如何传播并核验？ |

需要强调：这些是相互关联的活动，并非所有项目都按同一顺序执行。安全、权限、质量、来源、版本、责任和成本贯穿各环节。

本部分应链接全书目录，让读者按问题进入相关篇章。参考框架是本书提出的组织方式，应保留其工作版本状态。

### 第五部分：更新计划与参与方式

需要说明：

- GitHub 持续维护完整书稿、案例、模板、来源和修订记录。

- 欢迎读者提出问题、纠正错误、补充来源、提交反例、复现方法或分享适合公开的实践案例。
- 使用和贡献应遵循仓库正式授权与贡献规则，文章中的介绍不能替代正式条款。

文末设置清楚的阅读入口：仓库首页、当前文章对应的书稿章节、已完成的模板和参与说明。只链接实际存在的材料；尚未完成的部分直接标明进度。

## 每篇文章的编辑要求

一篇方法文章建议依次包含：具体困扰、原因分析、可执行方法、完整例子、检查方法和延伸阅读。复杂主题可以拆成多篇，但每篇至少交付一项可以独立使用的成果。

正文中的例子、实验和参考资料遵循[写作指南](../docs/WRITING_GUIDE.md)。引用书稿时记录对应章节及版本；如果公众号表达经过简化，仍应保留会影响结论的适用条件。

GitHub 延伸内容可以提供完整论证、更多反例、模板文件、实验记录和后续修订。文章不应只剩章节摘要，也不应把读者必须知道的操作条件留到链接之外。

## 节奏与修订建议

初期建议每两周完成一篇完整方法文章，每月集中整理一次书稿变更。短更新按实际进展发布。具体安排由维护者根据内容成熟度和审阅进度调整，详见[路线图](../docs/ROADMAP.md)。

书稿是持续维护的内容来源。公众号文章发布后，如果关键结论发生变化，应在后续说明或可编辑位置中提示修订，并引导读者查看对应的当前版本。
