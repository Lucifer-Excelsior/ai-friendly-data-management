# 写作指南

> 状态：初版建议，随样章和共创实践修订。本文规定编辑与证据呈现方式；作品使用和贡献授权以仓库的正式授权及贡献规则为准。

## 1. 全书共同回答的问题

每章从具体任务出发，交代数据在什么环节被谁使用，现有做法会遇到什么问题，推荐怎样改进，以及如何验证改进有效。

“AI 友好”应与可观察的任务表现联系起来。写作时同时考虑效果、效率、成本、维护负担以及访问约束，避免把某一种格式、架构或产品直接定义为通用答案。

正文尽量采用稳定、可迁移的概念；产品操作步骤和版本相关内容放入明确标注环境的案例。写清哪些建议适合个人使用，哪些依赖团队流程或系统能力。

## 2. 统一元数据

章节、文章、模板、案例和实验记录建议使用 YAML front matter。以下仅展示元数据结构，不能据此认定第 19 章正文已经完成；提交时应替换占位内容。

本节字段描述文档的编辑状态。模板中用于记忆、决策和任务上下文的字段则描述业务记录，采用各自的取值，例如业务记录可以使用 `kind: decision` 或 `status: proposed`。两种元数据不能混用；需要同时保存时，分别置于 `document` 和 `record` 命名空间，或将业务记录作为正文中的代码示例展示。

```yaml
---
id: ch-19
title: 记忆内容与分层组织
kind: chapter
status: outline
version: 0.1.0-draft
updated_at: "YYYY-MM-DD"
authors:
  - "实际作者的 GitHub 用户名"
reviewers: []
related_chapters:
  - ch-20
sources: []
---
```

| 字段 | 填写要求 |
| --- | --- |
| `id` | 稳定标识。章节采用 `ch-01` 至 `ch-24`；文章、案例等使用独立前缀，标题调整时尽量保留标识 |
| `title` | 与正文一级标题一致，直接说明主题 |
| `kind` | 使用 `chapter`、`article`、`template`、`example` 或 `experiment` |
| `status` | 使用 `outline`、`draft`、`in-review`、`reviewed` 或 `published`，按实际进度更新 |
| `version` | 内容版本；草稿应保留 `draft` 等明确状态，不能用版本号暗示已审定 |
| `updated_at` | 最近一次实质修订日期，采用 `YYYY-MM-DD` |
| `authors` | 实际作者的公开署名或 GitHub 用户名，不自动添加维护者 |
| `reviewers` | 实际完成审阅、并同意公开署名的审阅者；未审阅时保留空列表 |
| `related_chapters` | 关联的章节标识；文章应据此连接书稿 |
| `sources` | 正文引用的来源标识列表，与文末来源表对应；尚无来源时留空 |

项目维护者的公开 GitHub 标识为 [Lucifer-Excelsior](https://github.com/Lucifer-Excelsior)。维护身份不替代具体内容的作者或审阅者记录。

`reviewed` 表示完成约定范围的编辑审阅，不等同于同行评议、行业认可或所有结论均已实测。实测和示例状态需要在相应内容处单独说明。

## 3. 章节正文模板

章节可以根据主题调整篇幅，但应覆盖以下内容。

### 3.1 问题与适用场景

说明读者面对什么任务、使用什么数据、受到什么约束。给出足够具体的场景，并列出本章不处理或需要另行研究的问题。

### 3.2 常见做法与失败表现

展示数据组织方式如何影响任务。区分实际观察到的失败与为说明问题而构造的反例；不要通过刻意设置极端基线来证明推荐方案优越。

### 3.3 原则与方法

解释建议及其理由，说明成立条件、取舍和可能增加的工作。涉及经验性判断时，明确其来源和验证程度。

### 3.4 参考数据结构

给出字段、标识、关系、来源、版本、适用范围及必要的时间信息。说明哪些字段必需、哪些按场景选用；提供一份可读的最小示例。

### 3.5 实施步骤

按读者可以执行的顺序描述输入、处理、输出和检查方法。需要人工判断、额外权限或系统支持的地方应直接说明。

### 3.6 完整案例

交代起始状态、采取的改动、结果及其局限。示例中的日期、数值和组织名称如果是虚构内容，应明确标注。

### 3.7 验证与成本

说明比较对象、任务集、观察指标和主要成本。没有实测时提供验证设计，不填写虚构结果或估算成效。

### 3.8 适用边界与反例

说明哪些情况下方案可能无效、成本过高或带来新的问题；提供至少一种有代表性的例外或失败情形。

### 3.9 检查表与可复用材料

列出读者实施后应检查的事项，并链接已经存在的模板或案例。计划中的材料用文字标为“待补充”，不要提供看似可用的空文件链接。

### 3.10 来源与修订记录

列出支撑主要主张的来源、相关实验记录，以及会影响读者理解的重要修订。

## 4. 区分证据、建议、假设与示例

同一篇内容可能包含不同性质的陈述，应在相应段落、图表或案例附近标明，不能仅用文章末尾的一句话覆盖全文。

| 类型 | 推荐标记 | 应提供的信息 |
| --- | --- | --- |
| 可查证的外部事实或研究结果 | `依据` | 具体来源、出处位置、适用范围；转述结果时说明原研究条件 |
| 本项目实际执行的测试 | `实测` | 任务、环境、方法、样本数量、记录位置、结果和局限 |
| 作者提出的方法 | `建议` | 推理依据、目标、成立条件、代价及适用边界 |
| 尚待验证的判断 | `假设` | 假设内容、可能的反例、计划采用的验证方法 |
| 用于解释的构造材料 | `示例` | 明确其演示性质；虚构数据、模拟结果应逐项说明 |

仅阅读了研究摘要、文档或他人的结果，不能写成“本项目验证”。代码能够运行，也不能直接推导为任务质量提高。

模型生成的文字可以作为待审稿件或示例素材。涉及事实、引文、数据和效果的内容仍需核查；没有核查的内容保留为假设或待核实材料，不能补造参考文献。

## 5. 保证来源可追溯

### 来源记录

关键事实、具体数值、研究结论和技术行为应尽量引用原始论文、正式技术文档、原始数据或其他直接证据。提出原创建议时，应清楚标为本书的建议。

文末来源表建议包含以下字段：

| 来源标识 | 标题与作者或机构 | 发布或版本日期 | URL 或 DOI | 对应位置与主张 | 访问日期 |
| --- | --- | --- | --- | --- | --- |
| S1（模板占位） | 填写真实来源 | 填写可确认日期，无法确认则说明 | 填写实际地址 | 页码、章节、图表或具体段落，以及支撑的主张 | YYYY-MM-DD |

正文在相关主张附近使用可对应的来源标识或链接。上述占位行必须在正式提交前替换或删除，不应作为实际参考文献保留。

同一来源只支撑其实际覆盖的主张。将多个来源归纳成新判断时，说明这是作者的综合分析。网页、软件文档和研究预印本可能修订，应记录使用的版本或访问日期。

### 示例数据与衍生材料

对输入资料、切分结果、索引、上下文包、记忆条目和反馈记录，尽可能保留可以关联原始对象的标识与版本。公开展示前检查是否包含未获允许披露的信息、个人数据、密钥或其他凭据。

转引内容和第三方材料应保留必要的来源及使用条件说明。案例数据是否可公开，需要单独确认，不能以“用于学习”为由默认可以提交。

## 6. 让实验结论能够被理解和复核

涉及效果对比时，至少说明：

- 任务定义、样本来源、样本数量及选择方式。
- 基线与改进方案各自改变了什么，哪些条件保持一致。
- 使用的模型、配置、数据、检索和提示版本；影响结果时补充运行环境。
- 质量指标、错误类型、耗时、成本与人工处理量的计算口径。
- 是否重复运行、结果是否存在波动、有哪些失败案例。
- 可公开的输入输出和执行记录的位置，以及不能公开的部分对复核造成的限制。

评估 token 数量时应记录计数方法；比较成本时应记录计价依据和时间。减少输入长度或提高检索命中率，不自动等于任务效果更好，应结合最终任务结果讨论。

没有完成测试时，使用“验证方案”小节说明将如何比较，不提供“预计提升百分比”作为既定结论。小规模示例的观察不能直接推广为所有模型、行业或数据类型都适用。

## 7. 格式服务于任务

Markdown 适合表达层次清晰的说明、示例和可读记录，但不是唯一的 AI 友好格式。正文应根据数据特点讨论适当的表达方式，例如：

- 说明、规则和带来源的知识段落可以采用 Markdown。
- 字段明确的记录和输入输出契约可以采用 JSON、表格或数据库结构。
- 多模态材料应保留原始内容、定位标记和关联信息，不能只留下文字摘要。
- 大规模数据与运行状态需要合适的存储、索引、查询和更新机制。

不要在缺少验证的情况下规定通用的层数、块大小、标题数量或 token 上限。可以给出有条件的起点，并说明如何调整和验证。

区分任务指令、访问控制、外部资料和普通记忆的来源与可信程度。检索得到的文本或记忆内容不能因为采用了某种标题格式，就被当作可以改变系统规则的授权依据。

## 8. 书稿与公众号文章的关系

GitHub 书稿保存完整论证、案例、模板、引用和修订记录。公众号文章围绕一个问题提供可以独立使用的方法，再连接到相关章节和材料。

从书稿改编文章时，应记录所依据的章节和版本；文章中的简化不能改变原有结论的适用范围。书稿结论发生实质变化后，应在后续修订或文章说明中交代。

正文尽量采用清晰的段落、必要的对照表和准确的图示。避免只用术语替代解释，也不要为“干货”删去会改变结论的条件与限制。

## 9. 提交前检查

- 元数据与内容状态是否准确，作者和审阅者是否按实际贡献填写？
- 章节是否回答了明确问题，并提供方法、例子和验证路径？
- 外部事实、作者建议、假设、示例和实测结果是否能够区分？
- 主要主张是否有对应来源，来源是否实际支持这些主张？
- 是否包含未经验证的效果承诺、虚构引用或伪装为真实结果的示例？
- 模板与文件链接是否真实存在，计划内容是否清楚标注？
- 是否说明适用范围、维护成本和重要反例？
- 是否完成公开材料检查，并遵守仓库正式使用与贡献规则？
